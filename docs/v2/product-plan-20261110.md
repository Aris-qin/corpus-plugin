# corpus plugin 产品方案（评审稿）

版本：产品讨论汇总 v1.0  
日期：2026-11-10  
状态：各项原则已在讨论中确认；本文作为整体产品方案，等待用户审阅。  
阶段：产品方案，不是技术方案，不代表功能已实现或已上线。

## 1. 一句话定位

corpus 是全局研究资料库和中央资料管理员：保管、组织并提供原始资料、调研资料、项目参考档案、期刊画像和作者指引，为研究工作与 wiki 编译提供可追溯的内容。

它不是项目执行管理器，不是自动研究员，也不建立第二套 wiki 知识入口。

## 2. 产品目标

用户从项目或主题开始，能够快速知道：

- 已有哪些参考总览和调研报告，哪些已确认、哪些仍为草稿。
- 结论依据哪些资料，能否回到原文及具体位置。
- 内容最近何时更新、何时核查，当前使用是否需要重新核实。
- 尚有哪些资料缺口、争议和未完成的入库步骤。
- 同一篇文献是否已有、是否有正式发表版、勘误或撤稿信息。

原始资料全局共享，不因服务不同项目而重复保存，不以项目形成检索壁垒。

## 3. 与其他组件的分工

| 组件 | 主要职责 | 与 corpus 的关系 | 不应发生的职责重叠 |
| --- | --- | --- | --- |
| corpus | 资料保管、解析切片、索引检索、组织关联、版本和时效管理 | 提供资料和已有调研档案 | 不独立开展完整调研，不编译第二套 wiki |
| researcher | 搜索、筛选、研究、分析、讨论与形成调研成果 | 使用已有资料，提出新增来源和成果保留清单 | 不把所有中间产物自动变成正式资料 |
| wiki | 跨来源的知识归纳、整理和编译 | corpus 是重要资料入口；页面引用 corpus 来源 | corpus 不重复保存 wiki 编译正文，不提供重复的知识入口 |
| fact | 项目或轻量工作的目标、任务、进展、问题、决策、执行成果和当前状态 | 引用 corpus 参考档案并说明用途 | 不复制维护参考正文；corpus 不接管 goal/task |
| temp | 临时文件、测试及调研中间产物 | 经选择与确认后可转入 corpus | 不等同于正式资料库；长期调研不默认视为可丢弃临时文件 |

职责按工作性质划分，不强求内容完全没有语义交叉。例如专题报告可以包含分析，但仍是有时间、有来源、有适用范围的研究资料，不等同于 wiki 编译后的通用知识页面。

### 3.1 corpus 与 wiki 的更新关系

新资料或资料修订可能影响 wiki 页面时，提示可能受影响的页面及原因；用户确认后，再由 wiki 编译流程更新。

不因 corpus 入库就自动改写 wiki。可能影响的判断不应伪装成已经完成的逐条验证；具体关联和识别机制留待技术方案。

## 4. 内容体系

### 4.1 原始资料

包括论文、文献、官网文件、网页、指南、补充材料及官方模板等。

保留原文件或获取时的原始内容、来源及获取时间。解析文本、切片和索引是派生内容，不替代原件。切片需要保留可返回原文的位置依据。

原始资料不按 project 分库或划分独占归属。同一资料可以被多个项目、主题、报告和 wiki 页面引用。

保存并可检索不等于认可资料中的全部结论。

### 4.2 调研资料

包括期刊画像、专题调研报告、方法比较、项目投稿研判等。

它们由 researcher 与用户的调研、研判和讨论形成，corpus 管理和提供其内容，而不是自行承担研究责任。

需要区分来源事实、综合判断和不确定性；保留依据、适用范围、内容更新时间、最近核查时间及版本关系。

### 4.3 项目参考档案

每个项目有一份参考总览，说明研究问题、主要依据、当前判断、争议和资料缺口，关联原始资料与专题调研。

总览不抄录全部正文，不持有原始论文的项目专属副本。fact 只关联档案并说明用途，不维护第二份正文。

档案可持续修订；已确认的当前版本与历史版本分开。项目未正式建立时，专题调研仍可独立保存和使用。

## 5. 期刊画像与作者指引

### 5.1 通用期刊画像

同时包含可核查信息和一般性研判，但两者明确区分：

- 客观信息：收稿范围、文章类型、开放获取政策、费用等，注明来源与核查日期。
- 一般性研判：近期选题偏好等，说明依据与不确定性，不混写成官网要求。

“某个项目是否适合投该期刊、存在什么投稿风险”属于项目投稿研判，关联项目和期刊，不成为期刊的普遍属性。

### 5.2 作者指引

既保留原始页面、附件和官方模板，也保留整理后的要求清单。

清单覆盖篇幅限制、摘要结构、章节要求、参考文献格式、图表规范、补充材料、各类声明、投稿材料清单及官方模板。原指引未说明的内容标为未提供，不自行补造规则。

按原创研究、综述等适用文章类型区分；保留来源、获取时间、核查时间和版本。使用时提醒核查官方最新要求。

实际检查稿件、修改格式、准备投稿材料由 researcher 或写作流程执行，不由 corpus 接管。

## 6. 全局组织与检索范围

- 原始资料全局去重、共享，各项目均可检索全部资料。
- 项目、主题用于引用、组织与可选筛选，不是存储边界或默认权限隔离。
- 从项目进入时先展示项目相关总览，但底层找证据不能悄悄限定为当前项目已关联的文献。
- 明确要求“只查本项目关联资料”或其他范围时，才采用相应限制，并在结果中说明范围。
- 同一资料关联多个项目或主题只增加关联，不复制原件和正文。
- 向量检索不等于去重；如何识别文献身份、文件一致性和版本差异留待技术方案分别解决。

## 7. 日常使用流程

以下是业务入口，不预设工具数量，也不要求一个动作对应一个工具。

### 7.1 入库资料

用户说“入库”即授权正常规模的原件保存、解析、切片和索引，不逐步重复询问。

明确指定的项目或主题关联直接采用；不明确的先建议，再询问用户。未确认关联不应被悄悄写成确定归属，且原件不会因此变成项目私有。

大批量、长时间或额外付费处理提前确认。具体规模阈值留待技术方案和运行配置，不在本产品稿虚设数值。

corpus 不因收到一个研究主题就接替 researcher 联网开展调研。

### 7.2 检索与读取

默认主要从项目或主题进入，先展示：

1. 已有参考总览和调研报告，正式版优先，草稿明确提示。
2. 最近核查时间、待核查项和资料缺口。
3. 可继续展开的原始文献、证据片段和原文位置。

用户明确要求“找原文证据”时，直接检索原始资料及切片，不强制先读报告。

没有总览时明确说明不存在，继续提供可用资料，不虚构一份“已有总览”，也不把没有总览误报为没有文献。

### 7.3 整理关联

支持同一资料关联多个项目、主题、报告；调整关联不复制原始内容，不损坏已有引用。

有可靠原始来源的标题、作者、年份等元数据纠错，以及明确错误的关联调整，可以直接执行并留修改记录。

### 7.4 保存或修订调研档案

调研结束后列出建议保留清单，由用户一次确认。每项明确属于：

- 保存为原始资料。
- 保留为调研草稿。
- 确认为正式报告或正式参考版本。

用户一次确认后执行各项批准动作，不对已经明确批准的正式报告再次重复确认。仅批准保存不等于批准结论；尚未讨论成熟的内容仍是草稿。

改变调研结论或正式报告正文，需要用户确认，不以“元数据纠错”绕过。

### 7.5 核查与更新

主要在使用时提醒核查，不默认依赖定期调研，不自动启动 researcher。

普通查阅可继续展示旧资料，注明核查时间和待核查项；普通重复浏览不反复打断。

尚未核查的资料再次用于正式报告或投稿准备时继续提醒。是否重新调研由用户决定，不能只凭旧资料年龄就擅自宣布资料错误或失效。

## 8. 时间、版本与历史

### 8.1 调研资料

采用“当前版＋历史版本”，Git 辅助追溯；不以反复覆盖同一正文来抹去旧判断。

内容更新时间与最近核查时间分开。核查无变化时也可更新核查记录，不假装正文已经修订。

新版本说明改变了什么、为什么改变、依据是什么；旧版标为已被替代。尚未充分核实的内容标为待复核，而不是直接当作错误删除。

正常检索默认优先当前正式版，追溯时能展开历史。Git 的使用方式、提交边界及文件范围留待技术方案，不代表所有原件或索引都要提交 Git。

### 8.2 原始文献

同一文献同一版本不重复入库。预印本、正式发表版等作为同一文献下有关联的不同版本保留，不直接覆盖旧依据。

检索默认优先正式版，但保留特定版本的定位能力，不把旧引用悄悄改指内容不同的新版本。勘误、撤稿状态明确提示；有新版本不等于旧内容全部自动失效。

## 9. 入库状态与异常处理

分别呈现原件保存、解析、切片、索引是否完成，以及失败或部分完成的原因。允许针对失败步骤重试，不丢弃已保存原件，不把全部流程重做当作唯一恢复方式。

图表、公式等内容未完整提取时明确告知。只有摘要时标为“仅摘要”，不能作为全文入库成功，也不能据摘要生成声称覆盖全文的证据。

检索无结果需要区分：

- 当前库中未找到资料。
- 已有资料，但解析或索引尚未完成。
- 有相关资料，但不足以支持问题中的结论。

不把“检索不到”说成“客观上不存在”。可建议 researcher 补充，不自动启动外部调研。无结果解释应受实际可观测状态约束，不编造失败原因。

## 10. 去重、合并与删除

完全相同的文件直接去重；同一文献同一版本避免重复保存。疑似同一文献但内容不同、无法可靠判断的，先列差异供用户确认，不擅自覆盖或合并。

合并必须保留既有引用关系，避免 fact、wiki 和参考档案中的引用失效；具体稳定引用与兼容机制留待技术方案。

默认删除为停用或进入回收区，不直接永久删除。被其他档案或 wiki 引用的资料先提示影响范围。

撤稿、错误资料保留原件并标记状态，不直接抹去旧依据。永久删除必须获得用户明确确认，不能由清理缓存或临时文件的授权推导而来。

## 11. temp 与文件流转

已有项目的中间文件放项目自己的 temp；尚无项目归属的临时文件放公共 temp。

有价值的执行成果归对应项目；选定的原始来源和经研判的参考档案由 corpus 管理；fact 保留关联及用途说明。

长期调研不是临时垃圾，不因缺少项目归属就进入自动清理范围。temp 默认不自动删除，由用户决定保留、转存或删除。

“由 corpus 管理”在本稿指产品职责，不预设物理搬迁原件、跨目录复制或强制目录改造。

## 12. 用户权限与确认汇总

| 情况 | 已确认的处理原则 |
| --- | --- |
| 明确要求正常规模入库 | 完成原件保存、解析、切片、索引，不逐步打断 |
| 大批量、耗时或额外付费 | 执行前确认范围 |
| 项目、主题关联已明确指定 | 直接采用 |
| 关联不明确 | 建议后询问，不擅自确定 |
| 有可靠来源的元数据纠错 | 可直接纠正，保留记录 |
| 明确错误的关联 | 可调整并留痕 |
| 调研产物保留 | 列出带动作的清单，一次确认 |
| 正式结论或正文实质修订 | 用户确认后生效 |
| 版本不明或内容有差异的疑似重复 | 展示差异后确认 |
| 重新开展调研 | 提示，由用户决定并交给 researcher |
| 更新受影响 wiki | 提示影响范围，用户确认后再编译 |
| 永久删除 | 用户明确确认 |

## 13. 产品验收场景

以下是后续技术方案和测试必须覆盖的业务结果，目前不是测试执行报告。

| 场景 | 应达到的结果 |
| --- | --- |
| A、B 两个项目分别使用同一篇论文 | 仅一份同版本原始资料，两个引用；两项目均可全局检索 |
| 从项目进入，相关论文尚未关联该项目 | 全局证据检索仍可命中，不被项目默认过滤 |
| 说“入库”并指定主题 | 正常规模流程一次执行，指定关联采用，结果报告各步骤状态 |
| 原件保存成功但解析失败 | 原件保留，失败明确，可以只重试失败步骤 |
| 仅有摘要或图表提取不完整 | 检索和读取明确标注覆盖范围，不冒充全文完整 |
| 先有预印本，后补正式版 | 有版本关系，正式版优先，旧引用仍可追溯 |
| 调研结束，一次批准保留清单 | 原始资料、草稿、正式报告各按批准动作保存，不重复询问 |
| 使用陈旧投稿要求 | 展示核查时间和提醒，不伪装成当前官网要求 |
| 项目投稿研判与期刊通用画像并存 | 前者关联项目和期刊，后者不掺入项目专属结论 |
| 新研究推翻旧报告判断 | 新版有修订理由和依据，旧版标记被替代，可追溯 |
| 新资料可能影响 wiki | 提示页面及原因，不自动编译，不复制 wiki 正文入 corpus |
| 合并重复条目或停用有引用资料 | 引用不悄悄失效，影响可见，永久删除另外确认 |
| 无项目归属的长期专题调研 | 可以独立保存、检索，不被当成可自动清理的 temp |
| 检索没有足够证据 | 区分缺资料、处理未完成与证据不足，不擅自开展调研 |

## 14. 下一阶段待解决的技术问题

以下事项没有在本次产品讨论中确定，不能当作已获批准的实现选择：

- 现用插件、GitHub 源码与历史文档之间的实际差异，以及复用、替换范围。
- 工具数量、参数契约、业务动作与内部处理任务的划分。
- 原始资料、文献版本、报告及引用的身份标识，去重与合并机制。
- 原件、可编辑报告、派生切片与向量索引的存储结构和恢复边界。
- 状态与失败重试、长任务进度、费用及规模确认的执行机制。
- 当前版切换、确认与修订留痕的实现；Git 的具体范围与辅助方式。
- 旧项目化目录和已有资料如何接入全局库；不得直接据产品稿搬迁或重建。
- 期刊画像旧数据与 fact、wiki 引用的兼容交接。
- 使用时核查提示、wiki 影响提示的可实现程度和不确定性呈现。
- 隔离测试、真实资料副本演练、回退与上线验证方案。

后续流程：整体产品方案审阅 → 技术方案 → 独立审核与代码验证 → 测试 → 获准后部署。
