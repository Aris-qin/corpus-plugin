# corpus plugin 技术方案 v1.0（评审稿）

日期：2026-11-10。阶段：已确认产品方案后的技术设计，尚未获准编码、迁移或上线。

产品依据：`docs/product-plan-20261110.md`，用户已在后续对话批准产品方向。本文所有新增工具、表、命令、目录和默认阈值均是提案，不表示已经实现。配套 Xmind 是评审索引，字段契约以本文为准。

## 1. 结论与评审入口

建议采用：**单一 Python 业务核心＋Hermes 原生适配器；全局 SQLite 目录和内容数据＋内容寻址原件；调研不可变修订＋当前正式版指针；持久化分步任务；向量与全文混合检索**。

不按项目分库，不复制 wiki 编译正文，不把 researcher 的分析流程放入插件。项目与主题只提供多对多组织与可选过滤。主要入口建议六个，不要求继承 fact 的五工具数；内部动作分别校验，不提供万能 SQL/任意命令入口。

先复用已有 canonical、heading-aware chunking 和 generation 的思路及可验证代码；不要把旧 OpenClaw wrapper、硬编码路径、历史 worker 骨架直接包装上线。不引入微服务集群、专门向量数据库或自动调研调度器。

需审的技术取舍：

1. 六工具及其业务边界是否合适；数量可在真实模型调用验证后调整，不以数量作为完成标准。
2. 新建候选 schema v4 全局库，保留旧库只读回退，不直接原地改生产库。
3. 原件按哈希共享保管；调研修订以 SQLite 为发布真源、Markdown/Git 为可重建导出，避免双向写入冲突。
4. 持久化任务使用同一 CLI 包中的独立 runner，不在 Hermes 注册阶段自动启动后台服务。
5. 正式报告、实质修订、模糊合并、永久删除绑定具体提案；可信的人类批准渠道须 M0 验证，无可信通道不声称已强制防止模型自批。

### 2.2 已见到的关键实现差异

- 本地 `corpus_query` 要求 project，旧 CLI 的关键词召回与向量结果回查都 JOIN document_groups 限制项目；与新产品“全局证据检索默认不受项目限制”冲突。
- GitHub db.py、cli.py、chunker_markdown.py 与现用脚本哈希均不同，不能只换 wrapper 就认为获得了仓库新能力。
- 仓库 worker.py 的默认命令分发只有 health/query/score；默认 query 要求调用方提供 embedding。它不是完整的六入口后台服务。
- 旧 ARCHITECTURE 与 generation.py 的 ID 格式、manifest 主键不完全相同。未来以审过的代码契约为准，不照抄历史设计 DDL。
- 历史验收报告明确真实 embedding/rerank、生产库迁移与插件 socket 优先路径没有全部实测。本轮没有重跑旧测试，不把历史候选判定作为新版验收。
- 仓库仍带旧 fact-infra；新版 corpus 发布不得顺带安装、迁移或启用它。fact 使用独立项目已发布版本。

## 3. 运行架构与复用边界

```text
Hermes 六个业务工具 ─┐
                   ├─ 同一 Python application/service 层
管理 CLI 与任务 runner ┘       ├─ 校验 / 提案 / 事务 / 审计
                              ├─ 全局 catalogue.sqlite + chunks/FTS/vec0
                              ├─ 原件 blob / 不可变报告修订 / 派生代
                              └─ 外部 parser、embedding、rerank 适配器
researcher → 提供来源与调研成果；wiki/fact → 使用稳定引用
```

默认轻量查询和短写入在插件进程调用同包服务；重解析与 embedding 由持久化 runner 完成，工具返回 job_id，不阻塞一个 120 秒子进程等全文流程。独立 runner 使用同一配置和业务层，不再维护第二套 SQL。M0 测量冷启动与内存后再决定查询是否需要 Unix socket 常驻缓存；首版不把 socket 做成必要依赖。

parser 使用隔离子进程、超时、资源限制，不能阻塞查询线程；网络调用在事务外。数据库连接按执行单元创建，启用 foreign_keys、busy_timeout，写事务短小，使用 BEGIN IMMEDIATE，不使用 SQLite 不支持的 SELECT FOR UPDATE。

建议新增路径（未来源码位置，不是本次创建内容）：

```text
corpus_core/config.py, contracts.py, errors.py
corpus_core/catalog.py, identity.py, objects.py
corpus_core/parsers/, canonical.py, chunking.py
corpus_core/generations.py, embeddings.py, retrieval.py
corpus_core/references.py, journals.py, proposals.py
corpus_core/jobs.py, audit.py, exports.py, migration.py
plugins/hermes-corpus/plugin.yaml, __init__.py, skills/
cli/, tests/unit/, tests/contract/, tests/integration/, tests/migration/
```

把旧函数逐个移入可测试模块，不直接拷贝整份 cli.py。保留已有评分字段与公式信息，作为有来源的评估附注，不把论文类型或影响因子当科学结论可靠性的证明。默认相关性排序不让未审核的先验评分冒充人工核验。

## 4. 身份、内容与数据库模型

schema 名暂定 v4，与旧文档的 v3、fact 的 schema v3 完全独立。迁移器以真实 DDL 和数据特征识别输入；未知未来版本拒绝写入。

### 4.1 四种身份分开

| 身份 | 意义 | 不变量 |
|---|---|---|
| work_id | 同一知识来源/文献作品，随机稳定 ID | 不用项目 slug、标题或 PMID 作为唯一主键；无 PMID 文献也能入库 |
| version_id | 预印本、正式版、网页某次获取等具体内容版本 | 版本不可变；补充附件可共享 blob；预印本与正式版关系需可靠依据 |
| blob_sha256 | 一份原始字节内容 | 完整 SHA256 为唯一键，完全相同字节只存一次；不以向量距离去重 |
| generation_id | 某版本的一次解析/切片/索引构建 | parser/chunker/embedding 配置变化可产生新代，不改变版本本身 |

DOI/PMID/PMCID/URL 等存 external_identifiers，保存用户原始值和经过格式校验后的检索键；不静默“修好”错误标识。DOI 相同只说明候选身份相同，不足以证明两个附件字节或版本相同。URL 使用保守标准化，保留查询含义和原 URL；同 URL 新内容产生新版本候选。

### 4.2 逻辑表组（字段摘要，实施须给正式 DDL）

| 表组 | 关键字段/约束 |
|---|---|
| works | id, kind, title, metadata_json, revision, lifecycle(active/recycled/tombstone), created_at；kind=paper/web/guideline/template/other |
| external_identifiers | owner_id, scheme, raw_value, lookup_key, verification_source；同标识冲突进入复核，不覆盖旧记录 |
| source_versions | id, work_id, version_kind, acquired_at, coverage(abstract/fulltext/unknown), preferred 标记对应的受约束指针；内容不可变 |
| blobs / version_assets | hash, size, media_type, managed_path, role(main/supplement/template/web_snapshot)；多个版本或角色可引用同 blob |
| generations / chunks | version_id, canonical_hash, pipeline_fingerprint, state, counts；chunk 关联 generation＋节点/页码/偏移定位，不编码 project |
| embedding_profiles | provider, exact_model, dim, metric, preprocessing_version, provenance；不知道旧模型来源时明确 unknown |
| chunk_embeddings/vec0 | chunk_id, profile_id；不同模型空间分表/独立索引，维度相同不意味着可混检 |
| research_records / revisions | kind(topic_report/journal_profile/author_guidance/project_overview/submission_assessment/method_comparison), current_revision_id；修订 id, parent, body, hash, evidence, change_summary, reason, approval_ref |
| contexts / context_links | project/topic 的稳定 id、外部 fact 引用/slug alias；与 work/report 多对多，无项目独占字段 |
| journals | id, name, ISSN/eISSN/aliases；关联画像和作者指引，不以名称唯一认刊 |
| citations | from_revision_id, target_version_id/target_revision_id, generation_id/chunk_id 可选，locator_json；正文引用固定到版本 |
| review_events | 对象版本、核查范围、来源、时间、结论与 remaining_items；无正文变化也可追加 |
| external_links / impact_notices | wiki 相对路径或 fact URI、引用的 corpus 版本、关联依据、扫描时间；只存链接和影响说明，不存 wiki 正文 |
| jobs / job_steps | 状态、输入摘要、预算、租约、attempt、checkpoint、错误、产物校验及取消状态 |
| proposals / receipts / audit / export_outbox | 提案摘要、依赖 revision、授权记录、幂等回执、追加历史、导出任务 |
| legacy_map / migration_issues | 来源库身份、原表与主键、原始字段 payload、目标 ID、未决原因；旧 chunk 引用可查 |

关键约束：每份档案最多一个 current 正式修订；每项目最多一个有效参考总览；同版本与同 pipeline fingerprint 不并发建两份有效 generation；同一 context link 不重复。关系用 FK/唯一约束加运行时校验共同保证，不只靠提示词。

### 4.3 原件与报告正文

建议独立的数据根 `/workspace/projects/_corpus/` 延续全局职责；候选运行先使用隔离根。建议布局：

```text
catalogue.sqlite
objects/sha256/<前两位>/<完整hash>  # 全局原件，不按项目分目录
artifacts/<generation_id>/         # canonical/定位/派生附件
reference-exports/<record_id>/     # 当前 Markdown＋不可变修订导出
runtime/                           # 锁、runner 状态；非用户资料
backups/                           # 专门备份，不作为 Git 替代品
```

原件保管默认对选定资料进行独立 copy/reflink 并校验，不移动上传件或 temp 文件。相同字节共享对象，不共享可变路径的信任；迁移第一阶段允许只读 external locator 待保管，必须显示 external_unverified，不能承诺这些外部文件不会变化。最终生产切换前决定哪些外部引用已具备原件恢复保证。

为避免 DB 与文件双写真源，调研修订正文与结构字段在 SQLite 事务内保存；Markdown 是给人阅读与 Git 追溯的导出。不支持直接编辑导出文件后悄悄生效：检测 hash 漂移，导入为新草稿，需确认才能替换正式版。大附件仍在 blob，正文通过稳定引用关联。

## 5. 六个工具与严格参数契约

下面是拟议工具，不是当前已注册工具。每个请求返回统一 envelope：`ok, request_id, result, warnings, error{code,message,retryable,details}`。写入有 operation_id，重复 ID 同输入返回原回执，异输入报 IDEMPOTENCY_CONFLICT。严格限制未知字段、enum、长度、类型；bool 不接受字符串或整数冒充。

| 工具 | 用途和动作 | 必填与关键参数 | 不做什么 |
|---|---|---|---|
| corpus_ingest | preflight / submit | submit: inputs[], operation_id；每项 source(file/URL/identifier)、标识、已明确关联；可带 scope_approval_id | 不因研究题目自动搜索；不直接发布报告结论 |
| corpus_search | overview / evidence / similar | mode；overview: project/topic；evidence: query；scope 默认 global，显式 linked/filters 才限制；top_k 有界 | 不把当前 session/project 自动变成权限过滤 |
| corpus_read | item / version / chunk / history / resolve | ref、view；分页 cursor、上下文 include、use_context(browse/report/submission) | 不隐式核查官网、不生成无依据摘要 |
| corpus_reference | save_draft / propose / apply / reject | draft kind/body/evidence；apply 仅 proposal_id＋approval_ref＋operation_id | 不直接运行 researcher 或 wiki 编译 |
| corpus_manage | metadata / link / assess / review / propose / apply / recycle / restore | 按动作固定 payload；修改有 expected_revision；敏感动作先提案，apply 不允许替换正文 | 不接受任意表名、SQL、任意命令；不借纠错改结论 |
| corpus_jobs | status / list / retry / cancel | job_id 或 cursor；retry 有 operation_id，扩预算须新批准 | 不借 retry 绕过费用、范围、授权和权限 |

corpus_reference 管调研正文与正式版本，corpus_manage 管条目身份、元数据、关联和维护，不彼此提供同一正文写入口。查询与读取分别负责候选召回和精确展开；chunk 上下文及同层相似分别并入 read 与 search，不保留新旧双重写入口。

每个 action 发布独立 required/forbidden 字段表与运行时 tagged-union 校验。若模型供应商不接受复杂 oneOf，外层用兼容的 JSON Schema 并保留严格运行时校验，返回缺什么/多什么；不得为减少工具数量把校验删掉。M0/M6 真实模型测试比较调用步数、错误率与参数体积，再决定拆分，不恢复未经审查的旧接口。

典型调用：项目进入 `search overview(context=项目)` 返回档案/核查/缺口和草稿摘要；需要证据则 `search evidence(scope=global)`；选中后 `read chunk` 返回版本、页/节/偏移和上下文。没有项目总览可继续全局 evidence，不能伪造已有总览。

## 6. 入库、去重与可恢复任务

### 6.1 预检与授权

正常“入库”包含保存、解析、切片和索引，不逐步确认。preflight 可以由 submit 内部自动执行；需要额外确认时返回 NEEDS_SCOPE_APPROVAL，不先花费再问。

建议可配置起始阈值：一次超过 10 个文件、总字节超过 100 MiB、已知页数超过 300 或估计耗时超过 10 分钟时先出范围清单；这是技术建议，不是已测性能。额外付费 parser/OCR 总是先批准；既有 embedding 调用属于正常入库授权的配置内用量，但批量估算未知、超配置预算或可能产生新增费用时暂停询问。金额无法估算则如实注明，禁止显示虚构金额。

批准绑定清单 hash、服务、模型、单位/金额上限及有效范围；处理前复查输入文件 hash。新增文件、切模型、超上限需重新确认。任务不能因为断线重试重复消费已成功批次；远端无幂等保证的 ambiguous 状态要先查状态或提示潜在重复费用，不承诺严格 exactly-once。

### 6.2 状态机

job：queued → running → succeeded / partial / failed / waiting_confirmation / cancelled。step：pending → running → succeeded / partial / failed / skipped；租约过期标 interrupted，核对产物后续跑，不直接标成功。

步骤：validate → identify/hash → preserve_original → parse → canonicalize → chunk → embed → activate_index。原件已保存后后续失败不回滚原件；向量失败可先保留可用关键词检索，结果注明 retrieval_mode=keyword_only、coverage 和缺失数，不冒充完整向量入库。

复用成功步骤只在输入 hash、依赖 hash、pipeline fingerprint 均匹配时成立。切片器变化使下游作废，embedding 模型变化只重建该索引，不重做原件。取消不删除原件与成功历史；重新运行须走相同权限与预算检查。

### 6.3 并发去重与版本判定

相同 SHA256 用唯一约束和原子发布去重；同输入重试幂等。可信标识一致但正文不同：提供 candidate work 和差异，无法可靠判断则 waiting_confirmation，不覆盖现有版本。只凭标题、向量近似或正文参考文献中的 PMID 不自动合并。

预印本/正式版的同 work 关系要有可靠关联或用户确认；无可靠证据先保存为独立候选，保留来源，不冒充确定关系。新正式版优先是展示策略，不重定向旧引用。网页重抓只有内容变动才建立新内容版本，内容不变只增加获取/核查事件；抓取成功并不代表人工核查完成。

### 6.4 文件与事务原子性

原件先写 staging、校验完整 hash、fsync 后在同文件系统原子发布到对象路径；崩溃可能留下未引用 blob，由 fsck 列出而非自动删除。DB 仅在确认对象可读后提交引用。不能在网络请求期间持写锁。

generation 在 staging/building 下准备 canonical/chunks/FTS/vectors；校验数量、维度、profile、定位后，短事务切换 active 指针和 audit/outbox。失败不改上一 active 代。若只有关键词可用，明确记录 lexical_ready/vector_pending，与 complete 区分；新向量就绪的切换规则在单事务执行。

SQLite 不能与文件系统或 Git 做同一个原子事务；承诺的是“已提交引用不会指向未发布文件，残留可核查，重试可恢复”，不是跨系统完美原子。

## 7. 检索、定位、版本与证据边界

### 7.1 默认范围与结果组成

overview 按项目/主题找参考档案、正式报告、草稿提示、最近核查、缺口。evidence 默认全局，不携带隐式 project JOIN；显式 scope=linked 时才做项目/主题过滤，响应必须回显实际 scope。

采用向量召回＋FTS5 关键词召回＋可选 rerank。优先 RRF 等可解释融合，保留各路原始分值，不直接把不同量纲分数相加。FTS5 对中文的实际分词能力在 M0 使用中文 query 验证；不声称内置 unicode tokenizer 自动解决中文。必要时采用固定版本的中文预分词字段及可控词语匹配回退，不默认安装另一套搜索服务。

当前正式调研版优先；旧版/草稿可展开。原始证据默认找原始版本和切片，不拿报告总结伪装成论文原文。正式版论文优先，但撤稿/勘误状态必须突出；不同版本的关键差异不因排序被隐瞒。

过滤必须在候选生成或可证明覆盖的扩展过程中执行，不能“全局取 top10 再过滤”后误报无资料。若 vec0 无法高效完成过滤，在目标集合进行分块精确比较或扩大召回至预算上限；截断时返回 truncated 与候选范围，不宣称穷尽。同文多切片设置上限，按版本聚合，避免一篇长文淹没结果。

### 7.2 模型与降级

只有 provider/model/dim/metric/preprocessing 一致的 embedding 才能比较。旧向量标记 legacy_unknown，依据配置和历史证据核查，不仅看 1024 维就认定同模型。确认不能共用时先保留旧索引和关键词路线，提出有成本的分批重建计划；本次没有批准全量重嵌入。

真实 API 失败可以显式降级为关键词检索，不能以 mock 向量替代。测试 mock 模型使用独立 profile 和隔离根，生产模式拒绝 mock。rerank 失败显示实际使用的融合策略，不隐瞒降级。

### 7.3 稳定引用与定位

引用形式建议：`corpus://work/<id>`（导航）、`corpus://version/<id>`（固定来源）、`corpus://chunk/<id>`（固定 generation）、`corpus://reference/<id>/revision/<id>`（固定报告修订）。导航 URI 返回当前推荐版，证据引用必须固定版本；不把导航默认版变化伪装为证据未变。

locator 标明 page/bbox、XML节点、网页锚点、段落/字符偏移及定位基准 hash。parser 没有给页码则 page=null，不编造页数；Markdown 字符偏移不是原 PDF 偏移。表格、公式、图片/OCR未提取时保留 warnings 和 coverage。

重切片不删除被引用的旧 chunk/locator；旧 generation 退出默认检索但可精确读取。永久删除需要特殊墓碑说明，不承诺内容删除后仍能返回正文。

### 7.4 无结果与语义判断

返回可观测的状态：no_matching_results、processing_incomplete、search_degraded、candidate_budget_exhausted，并附相关条目状态。索引无命中不等于客观无资料；未检索全库也不能断言库里没有。

“证据不足以支持结论”是 researcher/模型的研判，不由一个零命中数自动生成。corpus 返回证据和覆盖限制，避免伪装科学判断。

## 8. 调研档案、期刊与作者指引

### 8.1 草稿、正式版本和一次保留清单

草稿也按不可变修订保存，草稿更新创建后续修订，不覆盖旧正式版。propose 冻结保留清单：每项 save_source/save_draft/publish_reference；包含正文 hash、来源、目标档案、expected_current_revision 与引用集合。

一次批准后执行已批准动作，不再次确认同一正式报告。长入库不能包在一个 DB 事务：先持久化批准与子任务，逐项报告状态；报告依赖的新来源未就绪时保持 approved_pending_dependencies，不把它发布成缺证据的正式版。彼此独立的清单项允许部分成功，失败重试不重复执行已完成项；结果明确逐项状态，不伪称整批原子成功。

current 切换、旧版被替代关系、引用、审计、提案消费、幂等回执同一事务。同期别人更新当前版时返回 REVISION_CONFLICT，展示差异后重新提案，不把旧批准套用到新正文。

正式正文变化必须说明 change_summary/reason/evidence；元数据纠错不能改正文、判断、适用范围或引文证据。回退旧结论同样是明确批准的当前版本变更，保留历史，不删后续版本。

### 8.2 期刊专用结构

journal_profile：分开 facts[] 与 assessments[]；每条有 source_ref、locator、checked_at、validity/uncertainty。费用包含币种、适用条件与采集日期，不把旧费用当最新。

author_guidance：以 journal_id＋article_type＋语言/版本适用条件组织；关联原始网页快照、附件与模板。每项 requirement 有 key、原文片段、整理值/单位、适用条件、来源定位、核查时间；没有规定的字段明确 not_provided，冲突或不明确标 unresolved。

要求清单覆盖：篇幅、摘要、章节、引用、图表、补充材料、声明、投稿材料与模板。整理清单由 researcher/用户提供并确认，插件只验证结构与出处，不自行编造规则。官网同一指引适用多种文章类型时共享来源，不重复保存。

submission_assessment 关联 project_context＋journal_id，包含匹配、风险和证据；不能混入期刊通用 facts。project_overview 包含问题、主要依据、判断、争议、缺口并关联资料，不强制所有专题先有项目。

## 9. 时间、核查与 wiki 影响

created_at / content_updated_at / acquired_at / checked_at 分开。所有新时间 UTC ISO 8601；旧时间原样保留在 legacy payload，转换不确定时保留 unknown，不虚构时区。

核查事件绑定具体对象修订与字段范围：例如只核查费用不能让作者指引全体显为刚核查。成功抓网页不等于人工研判可信；无变化核查只追加 review_event，不伪造新正文版本。

以使用时提醒为主，普通 browse 返回时效摘要不阻断；report/submission 每次返回尚未消除的提醒，不以“本 session 看过”压掉正式使用提醒。可配置参考阈值仅用于提示，缺省未配置则显示日期与未核查项，不自动断言过期或错误。corpus 不自动执行重新调研。

wiki 接口保存页面路径、corpus 来源版本及引用关联，不保存 wiki 正文，不把 wiki 作为第二种全文检索入口。用户许可后可只读扫描现有 wiki 引用约定，构建引用清单；不修改 wiki frontmatter/raw 布局。

直接来源引用发生版本变化、勘误、撤稿，生成确定的关联影响提醒；主题相似只标 possible_topic_match，并说明覆盖不全/尚未逐条验证。没有引用映射就明确无法定位全部页面，不声称“没有受影响页”。用户确认 wiki 编译是独立授权，corpus 正式报告批准不能顺带批准 wiki 修改。

fact 使用稳定 reference URI；corpus 对 fact 只读获取外部身份/别名，缓存只做目录，不维护 goal/task，不要求 fact 服务在线才能读取已经保存的档案。项目更名使用 stable ID/alias，不重写原件路径。

## 10. 确认、维护与安全

### 10.1 提案与人类批准

提案不可变 payload_hash＋依赖 revision＋影响清单＋授权范围；状态 prepared/approved/applied/rejected/expired。apply 不允许携带替换 payload。批准时不锁 DB；落地时乐观版本校验，防止 TOCTOU。

本机存在审批 transport 注册接口和观察 hooks，但没有在本轮证明 corpus 能获得与业务提案绑定、不可由模型伪造的批准凭据。**M0 必须在真实 WebUI 做端到端原型**，核验拒绝、跨 session 重放、模型伪造 confirm=true、正文变化等情况。观察到一次 approval hook 不自动证明本业务已获准。

如宿主不能提供可信批准：保留提案与对话审计的辅助模式，但明确不具备强制人类验证；敏感发布与永久删除改由用户控制的管理 CLI/确认入口应用。不能靠 LLM 自填 approval_ref 假装安全。产品确认意图不降低，具体接入方式是上线门槛。

### 10.2 合并、停用和永久删除

完全相同 blob 自动去重。条目合并保留别名映射；不同内容不直接揉成一个版本。先检查所有引用、清单、上下文关联和唯一约束，展示冲突后确认，事务内更新内部引用与映射，外部旧 URI 经 resolve 仍可解析到原版本，不悄悄改证据。

recycle/restore 留痕；被引用条目停用前先给影响清单，不因回收立即删除 blob。撤稿/错误状态保留原件和警示。

purge 先冻结影响清单与提案，再明确批准，二次校验引用集合 revision。共享 blob 仍被其他对象引用时不能删；先对目标去关联/墓碑，物理清理由可恢复 GC 步骤完成，失败报告 pending，不误称已彻底删除。外部未知引用无法穷尽，永久删除前必须明确这个限制。法规性立即删除或涉密处置不作为首版自动策略。

### 10.3 输入与外部请求

路径 realpath＋允许根限制，拒绝 traversal/越界 symlink/可执行附件；不自动修改权限或搬动源文件。URL 获取限制 http(s)、私网/环回/云元数据地址和每次重定向目的地，防 SSRF；合法 DOI/URL 的定点获取不等于主动搜索。身份验证墙不绕过，不把登录页当论文。

下载设置大小/类型/超时限制、断点状态与内容检测。敏感资料提交远端 parser/embedding 必须遵守已批准服务及隐私范围；日志不记录 key、token、全文和账户 URL。测试与生产配置明确隔离，不通过缺省路径自动连接旧库。

## 11. Git、备份与导出一致性

Git 只辅助版本追溯，不是 corpus 真源或全文索引。导出范围建议仅 reference-exports 下的报告修订、当前导航清单和安全元数据；排除原件、SQLite/WAL、向量、原始全文、缓存、密钥与任务运行日志。导出有 corpus_revision、body_hash、revision_id。

DB 成功后同事务写 export_outbox，重试生成临时文件并原子替换。导出或 Git 失败不把已生效的报告误报为失败：返回 committed=true、export_pending=true。Git 提交由显式配置或批准的批次执行，不自动 push；本次不创建 Git 仓库、不提交现有文档。

备份使用 SQLite backup API、对象清单及哈希；原件与 DB 要形成对应 manifest。派生索引可恢复，但重建费用/时间不能忽略。恢复验收必须精确读取旧引用、正式报告和原件，不仅跑 integrity_check。

## 12. 升级、接入与回退

### 12.1 为什么不原地直接升级

旧库以 PMID 作主键、含历史 project 前缀 chunk、自写内容分类和相对原件路径；新模型还需通用 ID、版本与报告生命周期。建议构造独立候选 DB/数据根，保持旧库不变，逐项对照后切换配置。目录调整和全量重嵌入均需另行批准。

### 12.2 迁移步骤（未来实施，不是已执行）

1. 读取现用配置、库/schema、原件根清单、旧脚本与插件版本；只导出非敏感配置。确认真实 SDK/扩展/模型环境，不能盲目在系统 Python 安装依赖。
2. 获准后用 backup API 创建一致副本，包含已提交 WAL；检查完整性和可恢复性。禁止直接 cp 正在写的主库或用 immutable=1 忽略活跃 WAL。
3. 在副本构造 schema v4，逐行导入旧字段及 NULL/时间表示，保存 legacy_map。418 等本轮数字只是当前基线，迁移时重新冻结并比较，不硬编码断言。
4. work/version 先按旧记录建立可追溯身份；同 DOI 冲突、不同 PMID 疑似同文、七条 self_written 分类、venue/source 混用都进入 migration_issues，不自动合并、不猜过去确认。
5. 项目和 document_groups 只变成关联；旧 chunk ID 原样登记 alias，保留树关系、评分、来源、正文、定位和向量映射。导入向量前逐条验证 profile、维度、chunk 对应，未知身份不擅自重嵌。
6. 遍历批准的原件候选根，输出旧路径→实际文件→hash→版本关系；缺原件与仅解析文本区分。已找到的样本不代表所有原件可用；不重新标记全文完整。
7. 处理旧 fact journals/其他期刊画像：先清点真实数据，版本化导入并保留旧键与来源。用户未批准的历史总结标 imported_unreviewed，不能伪造正式批准。旧自写 wiki 正文不批量复制进新 corpus；来源分类待复核的保留隔离，不自动销毁。
8. 对照全文 hash、每字段、关系、chunk locator、向量数量/profile、旧 URI、回收状态及未决项；未知关系明确报告，迁移不等于资料策展修复。
9. 只在副本做入库、发布、版本切换、故障恢复与模型测试，验证不会写真实根。产出可读迁移报告和 restore manifest。
10. 正式切换需另行授权：停止/封锁旧写入→捕获最终一致快照→重建或核对最终候选→切配置→安装 Hermes adapter→新 session 基本验证。旧脚本只读兼容，禁止新旧双写。

### 12.3 回退语义

切换前可丢弃候选，不动生产。切换后尚无新写入，可恢复旧代码/配置和一致快照。已有新写入时先停止写入、备份新状态，再决定修复前进或导出新增数据后回退；不能直接恢复旧备份并宣称无损。GC、永久删除和付费远端处理不可由数据库回滚撤销，单独记录限制。

旧 corpus 工具名称可短期提供只读兼容，明确旧 project 过滤语义与新默认范围差别；旧 score 写入口不得绕过新校验，新版六工具不同时曝光两套重复写 API。旧 TS fact-infra 不随 corpus 包安装。

### 13.1 最小测试矩阵

- 单元：标识格式/保守规范化、blob hash、版本关系、重复判定、严格参数、字段清空/缺省、时间与核查范围、路径/SSRF、安全日志。

- 数据完整性：同文两项目一份来源；原始资料无项目也可检索；同模型/不同模型隔离；原件/报告/定位/向量/FTS 与 active 状态一致。
- 故障：保存后解析失败；部分向量成功；外部 API timeout/429；响应丢失；DB busy；磁盘满；generation 切换前后 kill；runner 租约失效竞争；outbox/Git 失败。
- 确认：一批混合保存/草稿/正式；批准后正文改变；并发发布；拒绝/撤回；模型伪造批准；旧入口绕过；跨 session 使用已授权提案的有效性与作用域。

- 领域：作者指引按文章类型；官方事实与判断分开；not_provided 不造规则；核查无变化不新增正文；submission 每次提醒未决项。

- 迁移：活跃 WAL、一致快照、重复迁移、未知 schema 拒绝、相对路径、self_written 未决、字段/关系/旧 ID 保真、失败残留、切换后新增写入回退限制。
- 真实集成：实际安装 SDK 自动发现；六工具真实模型调用；小批真实论文/作者指引/网页快照端到端（额外费用先授权）；真实副本检索新旧对比，打包后复跑，不用 mock 成绩冒充真实 embedding。

### 13.2 隔离硬门禁

测试入口要求显式 sandbox_root；DB、raw、output、job 根必须 realpath 均在该根下，否则执行前退出。网络默认禁用，只为获准真实调用开启。不给测试读取生产 .env/配置的隐式回退。pytest 只收集规定测试目录，旧手工脚本不自动执行；CI 使用空 HOME/独立配置，禁止 fallback 到 /workspace/projects/_corpus。

独立验收在最终交付包而非仅开发目录执行，记录命令、退出码、环境、用例数和安全跳过原因；保留失败证据，不把静态校验与业务测试混报。

## 14. 主要风险与不做项

| 风险 | 应对/门禁 |
|---|---|
| 文档正确但旧库原件路径不可解析 | 完整原件清单与恢复演练；缺失透明，不直接批量搬目录 |
| 六入口掩盖大量分支 | action 固定契约，真实模型错误率验证；有证据才拆工具 |
| 旧向量同维不同模型 | profile/provenance 验证；不混检，不自动付费重嵌 |
| 宿主审批不能证明真实用户批准 | M0 原型；敏感操作 fail-closed/用户管理入口，不自填 bool |
| DB、文件、Git 多系统一致性 | 对象先发布、DB短事务、outbox；报告 committed 与导出分别状态 |
| runner 运维变复杂 | 一个可监督进程、持久化队列、锁与租约；不引入消息队列集群 |
| 收录调研越界成自动研究员 | 调研正文由 researcher/用户提供；corpus 管保存、结构、出处和版本 |

首版不做：自动定期调研、自动 wiki 编译、项目私有原始库、自动清理 temp、无许可抓取付费全文、无批准的大规模重嵌入、静默永久删除、第二套 wiki 知识入口。
